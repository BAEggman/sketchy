# Opus 실행 지시서 — Gemini 앱으로 한의학 그림 낭독 음성 만들기

작성일: 2026-11-20. 이번 문서는 실행 계획이다. 대량 음성 생성, 사이트 구현, 저장소 커밋 및 배포는 아직 수행하지 않았다.

## 1. 이번에 실제 확인한 것과 미확인 사항

| 항목 | 확인 결과 | 실행 시 의미 |
|---|---|---|
| Gemini 앱에서 음성 생성 | 사용자 Gemini 대화에 `memory_narration` 재생기와 46초 표시가 실제 존재했다. 이후 정확한 파일명으로 로컬 확인하니 WAV가 실제 2,217,644바이트였다. | 앱 경로를 우선한다. API 키를 필수 조건으로 요구하지 않는다. 표시값과 로컬 계측값을 구분한다. |
| WAV 재첨부와 ZIP | 기존 WAV 재첨부 및 `memory_narration_sample.zip` 일반 첨부를 Gemini에 요청했고 해당 첨부 UI가 실제 나타났다. | 파일 확보가 어려울 때 기존 생성물 재첨부·ZIP을 시도할 수 있다. 음성 재생성부터 반복하지 않는다. |
| 자동 다운로드 | 다운로드 이벤트 대기 3회가 각각 시간 초과됐지만, 이후 `memory_narration.wav`, `(1).wav`, `(2).wav` 및 ZIP이 실제 저장돼 있음을 확인했다. | 이번 실패는 실제 저장 실패가 아니라 이벤트·경로 반환 실패였다. 시간 초과만 보고 재생성하거나 다시 누르면 중복 파일이 생긴다. |
| Downloads 접근 | 사용자 후속 질문에 따라 `사용자가 지정한 Downloads 폴더`를 확인했다. 정확한 `memory_narration*` 이름 범위만 조회했고 WAV 2,217,644바이트, ZIP 1,783,362바이트를 확인했다. | Opus도 자기 실행환경에서 권한과 실제 저장 위치를 확인해야 한다. 다른 다운로드 파일이나 디스크 전체를 검색하지 않는다. |
| 브라우저 내부 다운로드 화면 | `chrome://downloads/` 이동이 브라우저 URL 정책에 의해 차단됐다. | 같은 차단을 다른 브라우저 명령·숨은 API·원격 디버깅·대체 브라우저 표면으로 우회하지 않는다. |
| 발음·음질 | 이 작업에서 실제 파일을 받아 전 구간 청취한 검수는 완료하지 못했다. | 재생기와 완료 문구만으로 발음·누락·대본 일치를 합격 처리하지 않는다. |

사후 파일 검증 결과: 원본 WAV는 24kHz·16bit·모노·46.2초이며 PCM 길이가 헤더와 일치했다. ZIP에는 안전한 상대 경로의 `memory_narration.wav` 한 파일만 있었고, 내부 파일과 별도 WAV의 SHA-256이 같으며 CRC 검사도 통과했다. 배포 후보로 96kbps 모노 MP3를 별도 변환했으며 555,308바이트·46.2초이고 전체 디코딩 검사를 통과했다. 이는 파일 무결성 확인이며 발음·내용·청취 품질 합격은 아니다. 샘플은 [검토 페이지](../../narration-review.html) 상단에서 재생할 수 있다. 원본 WAV·ZIP과 상세 계측 파일은 별도 전달 패키지에 보관하며, 이 공개 검토본에는 MP3 샘플만 HTML에 내장했다. 사용자 Downloads 원본은 변경하지 않았다.

샘플 대화: [사용자가 연결한 Gemini 샘플 대화]

이 대화에 나타난 대본 낭독 파일 생성은 관찰된 앱 기능이다. Google의 공개 Audio Overview 도움말은 팟캐스트형 생성·다운로드를 설명하며, 위 관찰이 같은 기능 또는 같은 내부 모델이라는 증거는 아니다. 앱 표시에 없는 엔진·목소리 ID를 추측해 기록하지 않는다.

## 2. 작업 목표와 우선순위

목표는 모든 카드를 무조건 녹음하는 것이 아니라, **그림과 사실에 맞는 확정 대본만 한 번 생성해 반복 사용**하는 것이다. 현재 범위는 한의학 Sketchy이고 생물학 허브까지 자동으로 확대하지 않는다.

1. 현재 배포 원본과 미게시 수정본의 버전을 고정하고 전체 목록을 만든다.
2. 기존 사용자 지적을 현재 카드 ID에 연결한다. 지적이 없다는 이유만으로 검수 합격을 부여하지 않는다.
3. 그림·정답·낭독 대본을 확정한다. 보류 항목은 음성 생산 목록에서 제외한다.
4. 대표 3카드로 소리와 다운로드 경로를 검증한다.
5. 작은 묶음으로 앱에서 생성하고 파일을 확보·검수한다.
6. 통과한 파일만 저장소에 업로드하고 허브에 연결한다.

새 소품·새 mnemonic을 대본 편집 중 임의로 만들지 않는다. 새 도안이 필요하면 별도 그림 재설계 과업과 사용자가 요구한 6개 독립 제안·7번째 심사 절차로 되돌린다. 아직 그림에 반영되지 않은 좋은 아이디어를 실제 보이는 장면처럼 읽지 않는다.

## 3. 카드·대본 확정 기준

### 데이터 우선순위

실제 확인된 최종 그림과 교재의 정확한 사실이 기준이다. 기존 `tts`는 참고자료이며 확정 정답이 아니다. `say`, `fact`, `hook`, `obj`, `attrs`, `answer`, `supplementAnswer`를 함께 대조한다. 예전 `tts`에 한자가 남아 있거나 조사와 숫자가 깨졌다면 그대로 녹음하지 않는다.

각 카드에는 다음 세 층을 분리한다.

- **장면 낭독:** 실제 보이는 소품·위치·행동을 짚고 소리 또는 뜻의 연결을 한 번 설명한 뒤 정확한 개념을 말한다.
- **보충 낭독:** 시험에 필요한 사실이지만 그림으로 직접 표현되지 않은 내용이다. “그림 밖에서 함께 기억할 내용입니다”처럼 층을 분명히 한다. 핵심 답을 짧게 만들기 위해 원문·목록을 삭제하지 않는다.
- **회상 질문:** 답을 말하지 않는 짧은 문장으로 분리한다. 회상 대기 시간은 플레이어가 부여하며 Gemini가 정확한 길이의 무음을 만들어 준다고 가정하지 않는다.

대본은 한글 독음으로 확정하고 화면의 한자 정답은 별도로 보존한다. 예: `杜仲`의 화면 표기와 `두충`의 낭독 표기를 별도 필드에 둔다. 동음어·이명·자호·저서명은 발음 사전의 전역 단순 치환만으로 확정하지 않고 문맥을 검토한다. 원문을 새로 보충해야 할 경우 교재 위치와 문헌 근거를 확인한다.

### 녹음 허용 조건

다음 조건이 모두 충족된 카드에만 `ready_to_generate`를 부여한다.

- 해당 카드에 열린 사용자 지적이 없거나, 해결 근거와 재검수 결과가 있다.
- 실제 최종 그림에서 대본이 지칭하는 대상·위치·행동을 확인했다.
- 그림 단서가 의미하는 답과 대본의 정답이 일치한다.
- 교재 요구 사실이 본문 또는 별도 보충 트랙에 모두 들어 있다.
- 낭독 한글, 숫자, 단위, 인명, 서명, 혈명에 미확정 독음이 없다.
- 원문→한글 대본→낭독 파일의 대응이 추적된다.

현재 작성되는 대본 초안의 기본 상태는 `draft`다. “사용자 미지적”, “문자 검토 완료”, “실물 그림 검토 완료”, “청취 검토 완료”는 각각 다른 필드에 기록한다.

## 4. 파일을 여러 번 만들지 않는 버전 체계

한 카드의 그림, 대본, 음성은 서로 다른 버전을 갖는다. 이미지 파일의 바이트가 바뀌었다고 음성도 무조건 다시 만들지 않는다.

| 필드 | 내용 |
|---|---|
| `card_id` | 기존의 안정된 강의·정거장 ID. 순서를 바꿔도 다른 카드 ID로 재사용하지 않는다. |
| `source_revision` | 사용한 저장소 커밋과 교재 판·문단 위치 |
| `image_asset_sha256` | 실제 표시 이미지의 바이트 해시. 화질·압축·색조 변경도 감지한다. |
| `scene_semantic_revision` | 낭독이 의존하는 인물·소품·행동·위치·정답 연결의 검수된 버전 |
| `spoken_text_sha256` | 최종 낭독 문자열의 해시. 문장부호·의도된 쉼 표기도 포함한다. |
| `voice_profile_revision` | 사람에게 승인받은 샘플, 음색 지시, 속도·억양 기준의 버전. 앱이 실제 표시한 설정만 저장한다. |
| `audio_key` | `spoken_text_sha256 + voice_profile_revision + generation_recipe_revision`의 해시 |
| `audio_sha256` | 실제 생성 파일의 해시 |
| `alignment_review` | 현재 그림과 이 음성의 의미 대응을 검사한 결과 |

색조·해상도만 바뀌고 낭독의 대상과 의미가 같으면 기존 음성을 재사용한다. 그림의 행동이나 위치가 바뀌면 먼저 대응 검수를 다시 하며, 낭독 문장이 여전히 맞으면 재녹음하지 않는다. 정답이나 발음이 바뀌거나 대본에 없는 물체를 가리키게 되면 해당 카드·해당 트랙만 수정하고 새 음성을 만든다. 과 전체·단원 전체를 일괄 재생성하지 않는다.

“같은 대본이면 Gemini가 같은 파일을 재생성한다”는 가정을 하지 않는다. 동일한 `audio_key`에 합격 파일이 이미 있으면 생성 요청 자체를 생략한다. 실패 후보도 검사 기록과 함께 보존하되 게시 목록에서는 제외한다.

## 5. Gemini 앱 실행 절차

### 시작 전 점검

1. Opus 실행환경에서 브라우저 조작 기능과 로그인된 Gemini 탭을 확인한다. 기존 선택 탭을 재사용하고 다른 계정으로 조용히 바꾸지 않는다.
2. 현재 샘플 대화를 읽어 성공한 요청 형태를 확인한다. API·AI Studio로 자동 전환하지 않는다.
3. 현재의 녹음 대상 목록과 정확한 대본을 로컬 작업 폴더에 동결한다. 미확정 카드와 보류 카드가 포함되지 않았는지 검사한다.
4. 다운로드 저장 위치를 확인한다. 관리 가능한 경우 이 작업 전용 폴더를 사용하고, 브라우저 전체 설정 변경이 필요하면 해당 작업에 대한 권한을 먼저 확인한다.
5. 최소 대표 샘플 3개를 고른다: 인명·저서명이 많은 카드, 본초명 또는 혈명이 많은 카드, 숫자·대조가 중요한 카드. 한의학 사실을 임의로 추가하지 않는다.

### 한 파일 요청 프롬프트

아래 형식은 Gemini 앱에 보내는 제작 요청이며, 메타데이터는 낭독 내용이 아니다. 앱이 프롬프트의 요구를 지켰는지는 결과 파일로 검사해야 한다.

```text
아래 [낭독 대본]만 한국어 음성 파일로 만들어 주세요.

작업 정보 — 읽지 마세요:
- 파일명: {card_id}__{track}__{audio_key_short}.wav
- 한국어 화자 한 명. 차분하고 또렷한 강의체.
- 인사, 제목, 파일명, 작업 번호, 설명을 음성에 덧붙이지 마세요.
- 대본의 단어와 순서를 바꾸거나 요약하지 마세요.
- 전문용어는 아래 한글 표기 그대로 읽으세요.
- 소리 연상 표현과 대응되는 이름은 분명하게 읽되 과장하지 마세요.
- 문장 사이에는 자연스럽게 쉬고, 단어를 한 음절씩 잘라 읽지 마세요.
- 코드나 대본만 반환하지 말고 실제 재생·다운로드 가능한 음성 파일을 첨부해 주세요.

[낭독 대본]
{확정된 한글 대본}
[/낭독 대본]
```

첫 샘플이 합격하면 같은 말투 지시와 기준 샘플 설명을 재사용한다. 앱에서 목소리 고정을 지원하는 설정을 실제로 확인하지 못한 경우 “목소리 고정 완료”라고 보고하지 않는다. 그림마다 음색이 달라지면 후보를 보류하고 다시 생성할지 검토한다.

### 묶음 크기와 큐

기본 제작 단위는 `card_id × track` 하나에 파일 하나다. 시각 지시·소리 연결·정답은 하나의 `main` 트랙, 보충 지식은 `supplement`, 회상 질문은 `question`으로 분리할 수 있다. 매우 짧은 문장마다 파일을 쪼개는 방식은 관리 비용과 연결 부자연스러움이 크므로 피한다.

처음에는 한 카드씩, 파일 확보가 안정된 뒤에는 3~5카드 묶음을 시도한다. 이는 앱의 공식 제한값이 아니라 초기 운영값이다. 묶음을 요청할 때도 각 카드가 독립 파일로 반환돼야 한다. 앱이 하나로 합쳐 읽으면 해당 묶음을 출판하지 않는다. 이어 붙인 긴 음성을 카드로 나누려면 정확한 경계 검증이 필요하므로 첫 운영에서는 한 카드씩이 낫다.

생성 작업은 `queued → generating → downloaded → audio_qc → accepted`로 기록한다. 원고 전체의 승인 상태는 `draft → ready_to_generate → generated → audio_qc_passed → published`로 기록한다. 작업 큐 상태와 콘텐츠 승인 상태를 혼동하지 않는다. 실패는 `generation_failed`, `download_unconfirmed`, `audio_qc_failed` 중 실제 원인으로 구분한다.

## 6. 다운로드와 검증 — 이벤트 실패를 파일 실패로 오해하지 않기

브라우저가 다운로드 이벤트와 로컬 경로를 정상 반환하면 그 경로만 확인한다. 경로를 받지 못했을 때는 다음 순서로 처리한다.

1. 다운로드 전에 예상 파일명과 작업 시작 시각을 기록한다.
2. Opus의 허용된 로컬 파일 도구로 지정 다운로드 폴더를 읽을 수 있는지 확인한다. 접근할 수 없으면 사용자에게 경로 또는 파일 전달만 요청한다.
3. 접근이 가능하면 지정 폴더의 **예상 파일명** 및 브라우저가 붙이는 중복 번호 후보만 비교한다. 다른 다운로드 파일 내용이나 사용자 전체 디스크를 검색하지 않는다.
4. `.crdownload`, `.part`, 0바이트 파일을 완료 파일로 취급하지 않는다. 크기가 안정됐는지와 디코더가 끝까지 읽는지를 함께 확인한다. 크기 안정만으로는 완전한 파일을 보장하지 않는다.
5. 파일 확장자뿐 아니라 WAV의 RIFF/WAVE 헤더 또는 실제 오디오 형식을 확인한다. 로그인 HTML이나 오류 문서를 `.wav`로 받은 경우 실패다.
6. `ffprobe` 등 이미 허용된 로컬 도구로 코덱·샘플레이트·채널·길이를 계측하고, 전체 디코딩 오류를 확인한다. 예상 길이는 이상치 탐지용이며 단어 누락 판정을 대신하지 않는다.
7. `SHA-256`을 계산하고 `downloaded_at`, 원래 파일명, 최종 파일명, 원고 해시, 실제 크기, 실제 길이를 기록한다.
8. 같은 파일이 이미 확보됐다면 다시 다운로드하지 않는다. 다운로드가 실패했다면 기존 음성 재첨부 또는 ZIP 첨부를 먼저 요청한다. 새 음성 생성은 별도의 작업이며 최후의 선택이다.

ZIP은 항목 목록을 먼저 확인하고 경로 탈출·절대 경로·실행 파일을 허용하지 않는다. 예상한 WAV 파일만 작업 폴더에 추출한다. ZIP 자체를 음성 합격의 증거로 삼지 않는다.

이번 세션에서 막힌 `chrome://downloads/`를 다른 명령이나 숨은 인터페이스로 우회해서는 안 된다. 로컬 파일 확인은 실행환경에서 독립적으로 허용된 파일 접근만 사용한다. 브라우저 정책이 특정 파일 접근까지 차단한 경우 그 제한을 터미널로 우회하지 말고 사용자에게 파일 전달을 요청한다.

파일 확보 단계마다 최대 3회 이내의 실제 시도를 허용한다. **이벤트 시간 초과 후에는 먼저 정확한 예상 파일이 실제 저장됐는지 확인한다. 존재하고 검증을 통과하면 다운로드 성공으로 종료하고 이벤트 누락만 진단 기록에 남긴다.** 똑같은 버튼을 연달아 누르지 말고 매번 화면·완료 상태·오류를 확인한다. 파일이 실제로 없는 경우에만 10초, 다음 실패 시 30초 정도의 간격으로 재확인하는 운영값을 쓰되 앱의 표시 대기시간과 제한 안내를 우선한다. 생성 완료에 몇 분이 걸릴 수 있으므로 화면에 생성 중이라고 표시될 때 재요청하지 않는다. 재시도 소진 시 다른 카드로 진행하고 실패 목록에 남긴다.

## 7. 음성 검수와 수정

음성 파일마다 최소 한 번은 전체 구간을 대본과 나란히 비교한다. 가능하면 음성 인식 결과를 보조로 사용하되 음성 인식기가 같은 전문용어를 틀릴 수 있으므로 자동 전사 일치율만으로 합격하지 않는다.

| 검수 항목 | 합격 기준 |
|---|---|
| 내용 보존 | 인명·서명·본초명·혈명·숫자·부정·대조·목록의 추가 및 누락 0건 |
| 발음 | 확정 독음과 일치. 다르게 읽은 단어는 원문·시각·실제 발음을 기록 |
| cue 전달 | 소리 연결의 양쪽 단어가 분명함. 재미를 위해 다른 용어처럼 변형하지 않음 |
| 읽지 말아야 할 정보 | ID, 파일명, 메타데이터, 괄호 설명 지시, “낭독 대본” 구분자 등이 음성에 없음 |
| 끝부분 | 마지막 문장이 잘리지 않음. 생성 완료 문구만으로 판단하지 않음 |
| 재생 | 모바일·맥 브라우저에서 재생·일시정지·탐색 가능 |
| 일관성 | 기준 샘플과 말투·속도가 크게 달라지지 않음 |

한두 단어가 틀렸으면 그 카드 트랙만 수정한다. 편집으로 짧은 부분을 이어 붙일 때에는 억양과 잡음·쉼의 불연속을 청취한다. 검수 실패를 덮기 위해 대본을 오독에 맞춰 고치지 않는다. 새로운 과학적·의학적 사실을 생성 도구가 덧붙인 경우 삭제 요청 후 다시 검사한다.

원본 WAV는 보존하고 배포본 MP3는 별도 생성한다. 처음에는 음성용 64~96kbps 모노를 비교 청취한 뒤 설정을 정한다. 이는 무조건 합격하는 음질값이 아니다. 정규화·무음 조정·인코딩 변경은 실제 문장과 전문용어가 손상되지 않는지 다시 확인한다.

## 8. GitHub Pages와 외부 음성 연결

GitHub Pages 전체의 제한이 24MB인 것은 아니다. 2026-11-20 공식 문서 기준 브라우저의 저장소 파일 업로드는 파일당 25MiB, 일반 Git 파일은 100MiB 초과 차단, 게시된 Pages 사이트는 1GB 이하다. 이번 묶음을 작게 유지하는 것과 서비스 전체 용량 제한을 구별한다. 장기적으로 많은 음성 파일을 관리하기 위해 외부 저장소를 선택한다.

GitHub에는 대본, 검수 기록, 파일 주소 목록, 플레이어 코드를 저장한다. 오디오 원본·배포 파일은 R2 같은 별도 파일 저장소로 분리한다. 브라우저에서 대형 오디오를 HTML의 Base64 문자열로 통째로 넣지 않는다.

운영용 R2 공개 제공은 사용자 소유 도메인을 연결하는 구성을 우선한다. `r2.dev`는 개발용이며 속도 제한이 있다. 업로드 이후 `Content-Type`, 실제 재생, 부분 다운로드와 탐색을 검사한다. 일반 `<audio src>` 재생과 JavaScript로 파일 내용을 읽는 상황의 CORS 요구는 같지 않으므로 사용하는 방식에 맞게 구성한다.

음성 주소 목록의 최소 필드:

```json
{
  "card_id": "lesson-id#station-number",
  "track": "main",
  "status": "audio_qc_passed",
  "script_revision": "reviewed-revision",
  "spoken_text_sha256": "actual-sha256",
  "scene_semantic_revision": "reviewed-scene-revision",
  "voice_profile_revision": "approved-voice-profile",
  "audio_key": "actual-content-key",
  "audio_sha256": "actual-file-sha256",
  "url": "published-audio-url",
  "duration_seconds": 0,
  "byte_size": 0
}
```

위 JSON은 스키마 예시이며 실제 파일·해시·길이·URL이 아니다. 빈 값이나 예시 값을 배포하지 않는다. 생성물 검수가 끝나기 전에는 URL을 공개 플레이어에 넣지 않는다.

플레이어는 처음 사용자가 재생 버튼을 누르는 동작을 받아야 한다. `audio.play()`가 거절되면 “재생하려면 눌러 주세요” 상태로 돌아간다. 재생 중이라고 거짓 표시하지 않는다. 이후 자동 넘김은 추정 초 수 타이머가 아니라 해당 음성의 `ended` 이벤트를 기준으로 한다.

- 현재 카드와 다음 카드만 우선 준비한다.
- 수동 카드 이동 시 이전 음성을 취소하고 늦게 도착한 응답이 새 카드를 덮지 않도록 요청 세대를 구분한다.
- 자동 넘김 켜기/끄기와 반복 범위를 별도 상태로 관리한다.
- 카드 구간 반복은 시작·끝 카드 ID로, 파일 안 A–B 반복은 시간 구간으로 구분한다.
- 전체 반복은 사용자가 선택한 재생 목록의 끝에서 처음으로 돌아간다.
- 음성 없는 카드와 재생 실패 카드는 기본적으로 정지·알림 처리한다. 건너뛰기 여부는 사용자가 선택하게 한다.
- “음성 생성 중” 상태를 “재생 중”이나 “완료”로 표시하지 않는다.

## 9. HTML 자동재생 때마다 Gemini 채팅에서 즉시 만드는 안

| 안 | 가능 범위 | 이번 선택 |
|---|---|---|
| GitHub Pages의 HTML·JavaScript만으로 로그인된 Gemini 탭을 조작하고 파일 받기 | 일반 웹페이지가 다른 출처의 로그인 세션과 DOM을 마음대로 읽거나 조작할 수 없다. iframe으로 바꿔도 동일 출처 제한이 사라지지 않는다. | 기본 구조로 채택하지 않음 |
| 별도 로컬 에이전트 또는 명시적 권한의 확장 프로그램이 Gemini 앱을 조작 | 기술적으로 구성 가능한 별도 시스템이다. 실행환경·로그인·탭·다운로드·UI 변경·생성 대기·요청량 제한에 의존한다. 일반 HTML만으로 동작하는 기능이 아니다. | 추후 선택 기능. 지금은 생산 보조 작업에 한정 |
| 서버에서 공식 음성 API를 호출하고 결과를 캐시 | 별도 인증·서버·비용 설계가 필요하다. 동일 대본은 저장 파일을 재사용할 수 있다. | 사용자가 앱 경로를 선택했으므로 이번 구현의 필수 조건으로 넣지 않음 |
| 앱에서 미리 생성하고 허브는 저장 음성 재생 | 기존 앱 성공 경로를 활용하고 검수된 음성을 일관되게 반복한다. | 권장 기본안 |

같은 오디오를 매번 새로 만들면 기다림과 음질·발음 변동이 생기고 매번 재검수가 필요해진다. 사용자가 원하면 미래의 로컬 보조 기능은 **음성이 없는 카드만 제작 요청 대기열에 넣고, 준비된 합격 음성을 재사용**하도록 설계한다. 자동재생이 Gemini 앱을 직접 호출하는 구조가 아니라, 학습 재생 큐와 제작 큐를 분리하는 구조다.

별도 에이전트·확장 프로그램이 실제로 설치·연결되지 않은 상태에서는 자동 생성이 된다고 표시하지 않는다. 계정 비밀번호·쿠키·세션 토큰을 HTML이나 Git에 넣거나, 접근 제한을 꺼서 구현하는 방법은 채택하지 않는다. CORS 설정만 바꾸면 타사 앱의 계정 조작 권한이 생긴다는 설명도 하지 않는다.

## 10. Opus 완료 보고에 필요한 증거

- 전체 카드 수, 초안 수, 녹음 보류 수, 녹음 가능 수, 실제 생성·확보·검수·게시 수를 각각 보고한다.
- 그림 실물 검수와 문자 검수를 구분한다. 표본 검사를 전수검사라고 부르지 않는다.
- 실패 카드마다 실패 단계, 실제 오류, 시도 횟수, 보존한 이전 합격본, 다음 조치를 기록한다.
- `audio_key`가 같은 카드의 중복 생성이 없는지 확인한다.
- 실제 파일의 크기·길이·해시를 기록한다. 앱의 답변 문구를 파일 계측값으로 대신하지 않는다.
- 샘플 3개 통과 후 작은 묶음, 그다음 전체 큐로 확대한다. 실패가 계속되면 큐를 멈추고 원인을 해결한다.
- 사이트 구현·원격 업로드·커밋·배포를 수행한 경우 각각 별도 완료 근거를 남긴다. 계획서 작성만 했으면 구현 완료라고 보고하지 않는다.

## 14. 이번 전달 파일을 사용한 실행 순서

### 사용자 니모닉 보존 — 2026-11-20 추가 지시

사용자가 만든 과장된 이야기, 소리 연결, 숫자 연상은 실제 의학적 사실과 다르다는 이유로 삭제하지 않는다. 예를 들어 ‘45세부터 위가 약해진다’는 족양명위경 45혈을 위한 사용자 니모닉이며 유지한다. 필요하면 ‘이 이야기에서는’처럼 암기용 설정임을 짧게 밝히고, 정답을 이어 말한다. 사용자가 만든 연결을 더 단정한 설명으로 대체하는 것은 문체 수정의 범위를 넘는다. 본문뿐 아니라 도입과 복습에서도 보조 연상·말장난·숫자 고리를 보존한다. 문법만 고쳤다고 주장하면서 연상 문장을 삭제하지 않는다.

현재 저장소 `539bab2a87625459874739246d0c5d8ca931d257`의 227과 2,067구간 전체를 `narrations.json`에 연결했다. 원본 정거장 객체와 수정 전 낭독을 보존했다. 문장 변경 994구간, 기존 문장 유지 1073구간, 보류 없는 검토 후보 1728구간, 녹음 보류 339구간이다. **녹음 확정(ready_to_generate)은 0개**이며 이는 음성 파일 생산 전에 남은 실물 그림·교재 대조를 생략하지 않기 위한 상태다.

1. [검토 페이지](../../narration-review.html)를 열어 원고·이전 원고·원문·보류 이유를 나란히 확인한다. [narrations.csv](narrations.csv)는 일괄 편집용이다.
2. 수정된 이미지·교재 DOCX와 실제 대응을 검사한다. 대본에 없는 모든 부가 사실을 무조건 삭제하지 말고, 필요하면 그림 밖 보충 트랙을 작성한다. 원문→독음→현대어 층을 구별한다.
3. `production_status=hold`인 구간과 같은 과의 종속 도입·회상 구간은 원인이 해결될 때까지 큐에 넣지 않는다. 기존 텍스트를 자연스럽게 고친 것은 사실·그림 불일치 해결의 증거가 아니다.
4. `retained_terms`는 확인할 항목의 목록이며, 거기에 단어가 있다는 이유만으로 음성 본문에도 있다고 판정하지 않는다. 숫자·혈명·저서·기여·부정·예외가 실제 narration에 유지됐는지 사람이 문맥을 읽고 확인한다.
5. 전체 의미 대조가 끝난 구간만 `ready_to_generate=true`로 올리고, narration의 SHA-256을 다시 계산한다. 생성 프롬프트에는 narration만 넣으며 original_tts, source_station, 보류 메모, ID는 읽히지 않는다.
6. 이번 MP3는 다운로드·재생 경로를 검증하는 샘플이다. 원고 전체의 발음 기준으로 승인됐다고 가정하지 않는다.
7. [추가판 대본 JSON](panel-narrations.json)의 `source_row`에 79판·740행의 원문을, `bagua`에 괘도 2종의 원문과 초안을 보존했다. 현재 227과의 대본과 중복되는 부분을 연결하고, 해당 초안과 실제 그림을 대조해 독립 판 낭독을 확정한다. 사암 요약행에서 전체 혈명표를 복원했다고 보고하지 않는다.
8. 그림·원문·대본·음성의 최종검수 결과를 별도 로그로 남긴 뒤, 합격 음성만 호스팅하고 허브의 실제 카드 ID에 연결한다. 이 공개 검토본은 검토 페이지와 원고 자료를 추가하며, 기존 학습 플레이어의 원고 교체나 대량 음성 생성을 포함하지 않는다.

이번에 사용한 원본은 전체 교재 DOCX가 아닌 현재 저장소 스냅샷이다. 따라서 ‘교재 전체 내용 누락 없음’, ‘모든 그림 시각 감사 완료’, ‘음성 청취 검수 완료’라고 완료 보고하지 않는다.

[panel-narrations.json](panel-narrations.json)에 79판 737행의 낭독 초안 및 제작 메모 제외 3행, 괘도 2종 대본을 추가했습니다. [검토 페이지](../../narration-review.html) 맨 아래에서도 볼 수 있습니다. 같은 JSON의 `source_row`와 `bagua`에 보존한 원문을 비교 자료로 사용합니다. 이 추가 원고는 별도 최종 그림·독음·내용 대조 전 초안이며 녹음 합격 상태가 아닙니다. 표 원본에 없는 사암 혈명표 전체를 생성했다고 간주하지 않습니다.
